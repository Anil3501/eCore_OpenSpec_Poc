# AGENTS.md

Orchestrator-driven, OpenSpec-based **Playwright-BDD** automation framework. A Jira story becomes
approved, traceable, executable tests through a durable workflow with **three human approval gates**.

Read [README.md](README.md) first — it documents the architecture, gate procedures, coverage model
and scaling design. This file only covers what an agent cannot discover on its own.

## Build and Test

```powershell
npm run preflight            # RUN THIS FIRST. Node version, deps, CLIs, browsers, env config.
npm run validate:artifacts   # 20 structural + semantic checks. RUN THIS AFTER ANY ARTIFACT EDIT.
npm run typecheck            # tsc --noEmit
npm run bdd                  # bddgen: features/approved/** -> .features-gen/
npm test                     # bddgen && playwright test
npm run test:smoke           # only @suite-smoke scenarios (also :regression, :critical)
npm run report               # open the last HTML report from reports/playwright-report/
npm run test:coverage        # forces V8 capture on when a local .env disabled it
npm run probe:api            # loopback check that the API client layer actually executes
npm run capture:session      # sign in once -> .auth/ecore-session.json for MCP exploration
npm run triage:failures      # classify failed results, preserve evidence, fingerprint them
npm run jira:fetch -- ETA-351 # REST fallback: fetch an issue verbatim into reports/jira/
npm run workflow:status      # read-only summary of every workflow instance
```

`validate:requirements`, `validate:workflow`, `validate:rtm`, `validate:defects` and
`validate:automation` run single scopes. All write `reports/validation/validation-<scope>.json` and
exit non-zero on failure.

**Jira access is MCP-first.** The official Atlassian MCP server is the primary path. When a session
exposes no issue-fetch tool, `npm run jira:fetch` is the documented REST fallback using
`JIRA_URL` / `JIRA_EMAIL` / `JIRA_API_TOKEN`. It writes a verbatim snapshot to `reports/jira/` and
**never** writes a governed artifact — promoting it into `requirements/raw/<JIRA-ID>.json` is the
requirement-analysis stage's job.

## Non-negotiable rules

These are enforced by [src/utils/semantic-rules.ts](src/utils/semantic-rules.ts) and by the Zod
models. Violating them fails validation.

1. **A chat message is never an approval.** Only a schema-valid JSON artifact on disk counts.
   Gate 1 → `requirements/approved/<STORY>-ac-approval.json`,
   Gate 2 → `test-plans/approved/<TP-ID>-approval.json`,
   Gate 3 → `features/approved/<capability>/<TP-ID>-automation-approval.json`.
2. **Never invent a business rule.** No role, error message, limit, timeout, security policy,
   validation rule, integration behaviour or regulatory requirement may be authored by an agent.
   Raise an `AMB-*` ambiguity instead.
3. **Never fabricate a passing result.** No `PASSED` without a real execution record. A coverage
   measure whose denominator is zero is `null` — never 0% and never 100%.
   **Browser code coverage is a different thing.** `npm run test:coverage` measures which
   application JavaScript executed and writes to git-ignored `reports/coverage/`. It must never be
   merged into `traceability/`, quoted as requirement coverage, or used as evidence that an
   acceptance criterion is satisfied.
4. **Never guess a locator.** Unverified locators stay marked `MCP_VALIDATION_REQUIRED` until the
   Playwright Planner validates them through Playwright MCP.
   **The same applies to an API contract.** An endpoint, field name or status code is never
   authored by an agent; an unverified one stays marked `API_CONTRACT_UNVERIFIED`. A guessed
   `DELETE` has side effects a guessed locator does not.
   A contract captured from live traffic is `OBSERVED`: it records what the application *does*, not
   what it *should* do, so asserting an acceptance criterion against it would make the current
   behaviour the definition of correct and a real bug would pass forever. `OBSERVED` may get a
   scenario to a state; only `HUMAN_APPROVED` (agreed at Gate 2) or `OPENAPI` may judge one.
   `SEM-API-CONTRACT` enforces this.
5. **No agent approves its own output.**
   **One scoped exception:** the `bug-analyzer` files a Jira bug without a fourth approval gate,
   because a red build must not wait on a human to be recorded. The compensating controls are
   mandatory: a failure fingerprint that is already `REPORTED` becomes a `DUPLICATE` instead of a
   second ticket, and every filed bug is assigned to `JIRA_BUG_ASSIGNEE_ACCOUNT_ID` for review. The
   agent still may not approve, alter or close anything it filed.
   A failure that never reached the application (DNS, TLS, proxy, refused connection, missing
   config) is classified `ENVIRONMENT_BLOCKER`: it is never healed and never filed. It proves
   nothing about the product, and filing it would erode trust in every real bug the framework
   files.
6. **Never edit `.features-gen/`** — it is generated by `bddgen`.
7. **Never commit a secret.** `.env` is git-ignored; `.env.example` holds keys with empty values.

## What eCore's API surface actually is

Do not assume a REST API exists. It does not, and assuming otherwise is how an agent ends up
inventing one. The full inventory, with evidence, is
[reports/validation/ecore-api-discovery.json](reports/validation/ecore-api-discovery.json).

eCore is a server-rendered Java application. **Sign-in is a form POST returning `302`** — there is no
login endpoint, no token, no JSON body. All primary navigation is full document requests. The only
AJAX lives under `/ssweb/setup/workspace/**/ajax/`, is RPC-style verbs ending in `.eo`, and takes
**form-encoded** requests, not JSON.

Three endpoints have been observed end to end. Two traps in them:

- `submitTransactionSearch.eo` lives under `/ajax/` but returns an **HTML fragment**, not data.
- `getWorkspaceTableData.eo` returns a DataTables envelope
  (`draw`, `recordsTotal`, `recordsFiltered`, `data[]`) in which **every business field is an HTML
  string** — `"<span title='...'>value</span>"`, not `"value"`. A Zod contract over it would be
  validating markup. It can seed state; it must never judge an acceptance criterion.

A further ~178 `.eo` paths are **declared** in the application's own markup but have **never been
exercised**, so they are `UNVERIFIED`: method, parameters, response and side effects are all unknown.
Several are irreversible against shared QA data (`deleteTransaction`, `voidDocument`,
`authorizeDestruction`, `mersTransfer`, `removeTransactions`). A path appearing in that list is
**not** permission to call it. Nothing enters `src/api/` until it has been observed with a captured
request and response shape.

To explore authenticated pages through Playwright MCP, run `npm run capture:session` first. The
`seed` project then resumes `.auth/ecore-session.json`, so a live password never passes through an
MCP tool argument and into the agent transcript. `bdd` and `technical` deliberately do **not** get
that shortcut — they must always exercise the real sign-in.

## Environment gotchas (these will bite you)

- **The shell is Windows PowerShell.** Chain with `;` — `&&` is a parse error. Two traps inside
  `node -e "..."`: an escaped `\"` in the inner JavaScript throws
  `SyntaxError: Invalid string escape`, and `||` can be rewritten to `;` in transit, producing a
  bogus `Expected ',', got ';'`. Use a ternary (`p.risks?p.risks:[]`) and single quotes inside.
  If a one-liner fails twice on quoting, write a throwaway script under `scripts/` instead.
- **A CLI `--reporter` flag REPLACES the config reporter array, it does not add to it.**
  `playwright test --reporter=list` therefore silently skips the `html` and `json` reporters, and
  `npm run report` then opens a stale or blank report that looks like "no tests ran". To narrow a
  run, use `--grep` / `--grep-invert` and leave the reporters alone.
- **Node 24 native type-stripping is the runtime.** Relative imports **must** carry an explicit
  `.ts` extension: `import { env } from '../utils/env.ts'`.
- **`erasableSyntaxOnly: true`.** TypeScript parameter properties
  (`constructor(private readonly page: Page) {}`) are a **compile error**. Use an explicit field
  plus an assignment in the constructor.
- **Do NOT add `"type": "module"` to package.json.** The warning is suppressed with
  `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON` in the npm scripts.
- **`tsc --noEmit` does not catch CommonJS interop failures.** Files here run as ESM, so a named
  import from a CJS dependency typechecks and then throws
  `SyntaxError: Named export 'x' not found` at runtime. Default-import and destructure instead
  (`import pkg from 'cjs-dep'; const { x } = pkg;`) — see
  [src/utils/coverage-report.ts](src/utils/coverage-report.ts). Always execute a script once after
  adding a dependency; typecheck alone proves nothing.
- **npm E403 from `registry.npmjs.org` is a recurring trap.** It has blocked this user in multiple
  sessions. Public npm is firewalled; the corporate Artifactory registry must be used. Project-level
  `.npmrc` is **not** inherited by `npm install -g` or by `npm init` / `npx create-*` run outside the
  repo — those need the registry configured at **user level** (`~/.npmrc`). If you see
  `403 Forbidden - GET https://registry.npmjs.org/...`, this is the cause; do not retry the same
  command or blame the package name.
- **A stage's tooling is not checked by the stage's `requires` list.** Every `requires` entry is an
  artifact path, so a missing CLI stays invisible until the stage shells out to it and fails. Run
  `npm run preflight` before starting or resuming a workflow. The OpenSpec CLI is
  **`@fission-ai/openspec`**, a pinned devDependency — the bare name `openspec` on npm is an
  unrelated 2019 name-squat (`0.0.0`, maintainer `akerust`) and must never be installed. Never
  install a workflow CLI globally: `npm install -g` does not inherit the project `.npmrc`.
- **The repo `.npmrc` contains a plaintext token.** Pre-existing, REVIEW_REQUIRED. Do not modify it
  without asking.
- **`.gitignore` is verified by observation**, not by assumption: `.env`, `.npmrc`, `.auth/` and
  `.playwright-mcp/` all stay out of `git status`. Re-check after adding any file that holds a
  credential, a session or captured application data.

## Architecture

The **SDD Workflow Orchestrator** owns all state and every handoff. It runs **one stage per
invocation**, then persists state. Stage order, per-stage agent, required inputs and outputs are
data, not prose — see
[workflow/definitions/sdd-jira-to-automation.workflow.json](workflow/definitions/sdd-jira-to-automation.workflow.json).

For the file-by-file list of everything one story creates, in stage order, with the reference
`ETA-351` filenames, see
[docs/framework-file-creation-sequence.md](docs/framework-file-creation-sequence.md). Consult it
before creating an artifact rather than guessing a path.

| Directory | Contains | Owner |
| --- | --- | --- |
| `workflow/instances/` | Durable state, one JSON per story+release (`WF-<STORY>-R<release>.json`) | Orchestrator only |
| `requirements/` | `raw` → `normalized` → `approved`, plus `reviews`, `examples`, `schemas` | Jira Requirement Analysis |
| `test-plans/` | `generated` → `approved` | Orchestrator (`TEST_PLAN_GENERATION`) |
| `features/`, `steps/` | Gherkin behaviour + thin step orchestration | Orchestrator (`BDD_DESIGN`, `IMPLEMENTATION`) |
| `src/` | `pages`, `components`, `fixtures`, `services`, `models`, `utils`, `api` | Orchestrator (`IMPLEMENTATION`) |
| `test-data/` | Fabricated inputs, one `<capability>.sample.json` per capability. Never a secret | Orchestrator (`IMPLEMENTATION`) |
| `defects/` | Governed defect reports (`DEF-*.json`) plus `defects/schemas/`. Evidence copies live in git-ignored `reports/defects/` | Bug Analyzer |
| `traceability/` | Capability-partitioned RTM, coverage, lookup index, executions | Orchestrator only |
| `openspec/`, `.github/prompts/opsx-*`, `.github/skills/openspec-*` | Spec layer | OpenSpec (tool-owned, do not hand-edit) |

**The workflow definition is the authority on who performs a stage, not this table.** Ownership
above is derived from each stage's `agent` field. The orchestrator may delegate `IMPLEMENTATION` to
`playwright-test-generator`, but only if that agent's definition is compatible with the installed
playwright-bdd setup; otherwise it does the work itself. `playwright-test-planner` is assigned to
`PLAYWRIGHT_VALIDATION` — it validates an approved plan against the running application, it does not
author one.

Two agent files are deliberately not assigned to any stage. `playwright-test-healer` and
`playwright-test-generator` are tool-provided and may be regenerated, so their files are left
untouched; `governed-locator-healer` is the governed wrapper the workflow actually calls. Neither is
an orphan to be cleaned up.

Scaling to 3,000+ tests relies on **capability partitioning** (one RTM file per business capability)
plus [traceability/index/lookup.index.json](traceability/index/lookup.index.json) so nothing is
scanned linearly. Never create a monolithic RTM.

## Conventions

**Every artifact carries a stable ID.** Merges are by key, never by position.

| Kind | Pattern | Example |
| --- | --- | --- |
| Requirement | `REQ-<JIRA>-<nnn>` | `REQ-ETA-351-001` |
| Acceptance criterion | `AC-<JIRA>-<nnn>` | `AC-ETA-351-002` |
| Ambiguity | `AMB-<JIRA>-<nnn>` | `AMB-ETA-351-001` |
| Test plan / scenario | `TP-…-<nnn>` / `TS-…-<nnn>` | `TP-ETA-351-001` |
| Trace | `TRC-…-<nnn>` | `TRC-ETA-351-001` |
| Approval | `APR-{AC\|TP\|AD}-…-<nnn>` | `APR-AC-ETA-351-001` |
| Defect | `DEF-<JIRA>-<nnn>` | `DEF-ETA-351-001` |

Regexes live in [src/models/common.model.ts](src/models/common.model.ts).

**Every artifact type has two definitions that must stay in sync**: a JSON Schema (for humans and
tooling) and a Zod model (for runtime). Change one → change the other, or `*-STRUCTURE` parity
checks fail. See [src/utils/schema-parity.ts](src/utils/schema-parity.ts).

**Layering is strict:**
- Feature files describe business behaviour only — no selectors, no page-object method names.
- Step definitions orchestrate only — no locators, no hard-coded data, no multi-page workflows.
- Page objects own locators. Prefer `getByRole` → `getByLabel` → `getByPlaceholder` → `getByText`
  → `getByTestId`. **No XPath, no nth-based selection, no long CSS chains, no `waitForTimeout`.**
  `SEM-AUTOMATION-HYGIENE` enforces this. A string-selector `.locator('…')` or `getByTestId` needs a
  `VALIDATED -` comment above it; a `waitForTimeout` needs `JUSTIFIED-WAIT:`. XPath, `.nth()` and
  `test.skip/fixme/slow` have no waiver. `MCP_VALIDATION_REQUIRED` is allowed during generation but
  fails the build once the file backs Gate 3 approved automation.
- **API clients own endpoints, the way page objects own locators.** They live in `src/api/` and
  extend `ApiClient`; Zod response contracts live in `src/models/api/`. A step calls a client and
  never issues a request itself. Parse the **whole** response against its contract — spot-checking
  three fields and ignoring forty is the API version of a test that never looked. No absolute URLs,
  no `process.env`, no response body in an error message. A `.delete()` or `.put()` against a shared
  environment needs a `CLEANUP -` waiver naming how the data is restored.
- All config goes through [src/utils/env.ts](src/utils/env.ts). **Never read `process.env`
  directly.** That includes [playwright.config.ts](playwright.config.ts), which uses `env.isCi`
  rather than `process.env.CI`. Requirements are enforced lazily (`requireBaseUrl()`,
  `requireCredentials()`, `requireEcoreLogin()`) so scaffolding works without secrets. Errors name
  variables, never values.

**Every Gherkin scenario needs traceability tags**: `@release-`, `@capability-`, `@req-`, `@ac-`,
`@tp-`, `@ts-`. Missing any prefix fails `SEM-FEATURE-TAGS`. See
[features/approved/account-access/organization-sign-in.feature](features/approved/account-access/organization-sign-in.feature).

A scenario also carries `@interface-api` or `@interface-hybrid` when its approved test plan declares
one. **A missing `@interface-` tag means UI**, so every file written before API support existed is
still valid and still correct without being edited. `SEM-API-CONTRACT` fails the build when a tag
and its plan disagree.

**An API failure is not a locator failure.** An `@interface-api` defect never enters
`LOCATOR_HEALING` — it exercises no locator, so the healer would burn both attempts against a DOM
the test never touched and the defect would reach Jira described as a locator bug it never was. Use
`CONTRACT_MISMATCH` (the call completed but violated the approved contract), `APPLICATION_DEFECT`,
or `ENVIRONMENT_BLOCKER`, and route straight to `BUG_REPORTING`. An API-only failure has no
screenshot: its evidence is the redacted request/response pair in `evidence.apiExchanges`.

**Browser code coverage does not measure API tests.** An API-only scenario never loads the
application's JavaScript, so it contributes nothing to `reports/coverage/`. Converting UI scenarios
to API scenarios will lower that number without lowering requirement coverage — another reason it is
never evidence about an acceptance criterion.

**Synthetic data is labelled `SAMPLE_DATA`** and must never mix with `REAL_JIRA_DATA` in one
artifact. The rule and its `SEM-SAMPLE-ISOLATION` check remain in force, but **no synthetic story
remains in the repository**: the `SAMPLE-101` and `SAMPLE-900` scaffolding stories were both removed
on 2026-08-27. `ETA-351` is the reference example for every artifact shape.

**A negative scenario must never use the real account.** The eCore login page warns that an account
can lock out after a configured number of incorrect attempts. Wrong-credential and missing-field
paths therefore use fabricated values from `test-data/<capability>.sample.json`
(`dataClassification: SYNTHETIC_INPUTS`); only the happy path calls `env.requireEcoreLogin()`. See
[src/services/organization-login.service.ts](src/services/organization-login.service.ts).

## Out of scope

Do not create `src/agents/` or `automation-agents/` — agents live in `.github/agents/` as
`*.agent.md`.

The `bug-analyzer` triages, evidences and files failures. It does **not** diagnose application root
cause, assign severity or priority, or manage a bug after it is filed. Those are human judgements
and an agent may not invent them.
